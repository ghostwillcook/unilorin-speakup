# API-CONTRACTS.md — Section-by-Section Shape

**Optional** — only create this file if the feature has a real client-server boundary (a backend the feature calls into, over any protocol). A purely client-side feature (e.g. local-only mobile UI with no network call) never gets this file. Decided by the Job 1 interview in `SKILL.md`.

Before writing your first one, read `examples/account-signup/` (a small, validator-clean, backend-only example bundle bundled with this skill for exactly this purpose) — especially its `API-CONTRACTS.md`. Match its shape rather than improvising the format from prose alone.

**Check for an existing contract system of record before inventing one.** Many teams already document every endpoint somewhere outside this bundle — a Confluence space with one page per endpoint, an OpenAPI/Swagger doc, a Postman collection — and that documentation is often more current than a PRD's prose description of what an endpoint returns, especially mid-implementation. If a connected tool can reach it (a Confluence/Atlassian MCP tool, a repo's OpenAPI file), look there for the feature's actual endpoints before drafting `API-CONTRACTS.md` from the PRD alone, and prefer the live contract's schema over the PRD's when they disagree — a PRD's stated *approach* (e.g. "check field X to distinguish case A from case B") can lag behind an already-shipped, more direct mechanism (e.g. an explicit boolean flag added to the response for exactly that distinction). If you find a real conflict between what the PRD says and what the live contract already does, surface it to the user rather than silently picking one — it usually means the PRD text is stale relative to work already in flight.

One H2 per endpoint/operation (`## 1. Signup`, `## 2. Login`, ...) — H2s are numbered like every other technical file, but everything below is H3+ and unnumbered (a plain heading title, not `3.1`). Each H2 has four parts, in this order:

1. **One-line prose summary** — what the endpoint does and when it's called. This is what a QA/PM reader who doesn't want to parse a schema reads first.
2. **`### {METHOD}: {PATH}`** — the protocol-specific operation line. Pick whichever form fits the surface:
   - REST: `### GET: /signup` (method + path)
   - GraphQL: `### Mutation: signUp` (operation type + name)
   - gRPC: `### RPC: AccountService.SignUp` (service + rpc)
3. **`### Request`**, broken into `#### Query Params` and/or `#### Body` — each a `Variable | Type | Description` table. This is flat data (a name, a type, a one-line description per field), so it belongs in a table per the bundle-wide rule ("flat facts go in a table") rather than a yaml block — a table is what QA/FE actually scan, not indentation. For a body with real nesting, use dotted paths as the `Variable` name (`address.street`, `address.city`) instead of forcing multiple table levels; only fall back to a fenced yaml/json-schema block for the rare deeply-nested or polymorphic body a flat table genuinely can't represent. Follow the tables with a runnable `curl` example — it's the one artifact a type table can't give you, and it's what FE/QA copy directly into a terminal or Postman.
4. **`### Response Schema`**, one `#### <SchemaName>` per named shape (e.g. `#### SignupResponse`, `#### ErrorResponse`), each a `Variable | Type | Description` table the same way `Request` is. If two or more endpoints in this file share the exact same error shape, define it once instead of retyping the table per endpoint — either under the first endpoint that needs it, or (if the whole file leans on a shared shape like a common `ErrorResponse`) as its own `## 1. Shared Types` H2 *before* the first endpoint, in which case every endpoint H2 shifts down (`## 2. Signup`, `## 3. Login`, ...) since H2 numbering still starts at 1 like every other technical file — there's no `## 0.` exception.
5. **`### Example`**, one `#### {STATUS} - {Short Label}` per status/error code, each with a one-line description of *when* that status fires (the trigger condition — this is the piece a bare status+label heading can't convey on its own) followed by a fenced `json` body. Reference the `EC-N` it corresponds to when one exists (`**Reference**: EC-1`), so the trigger condition traces back to `SPEC.md` — this is the one place this file points back into the requirements. Include at least the success case and one error case; don't skip straight to just the happy path.

If a feature has genuinely separate contract surfaces (e.g. a public API and an internal BackOffice API), group endpoints under platform-labeled H2 groups the same way `TEST-SPEC.md` does, rather than flattening everything into one undifferentiated list.

No IDs are defined in this file — endpoints are referenced by name/section, not by ID.
